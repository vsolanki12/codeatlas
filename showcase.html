HyperShift Atlas

A code intelligence platform that automatically discovers, maps, and explains the HyperShift architecture — directly from source code.

Atlas never invents architecture. It extracts it.
Go CLI tool 68 tests passing 7 packages 9 ADRs 0 external deps (Go stdlib + sigs.k8s.io/yaml)

The Problem

HyperShift is a large, fast-moving codebase. Understanding it today is hard.

Scattered Knowledge

Architecture lives across Go files, CRDs, markdown docs, design proposals, and tribal knowledge. No single place connects them.

Hidden Relationships

Changing one controller can silently affect others. These dependencies exist in code but aren't visible until something breaks.

Onboarding Friction

New engineers spend weeks building a mental model that could be generated in seconds from the source code itself.

Documentation Drift

Written docs fall out of sync with implementation. The code is always the truth, but reading raw code doesn't show the big picture.

Atlas solves this by treating source code as the single source of truth and generating architecture from it.

Execution Pipeline

1 Configuration — parse CLI flags, resolve repo path cmd/atlas
2 Repository Validation — verify path exists and is a directory discovery
3 File Discovery — walk tree, skip .git/vendor/node_modules discovery
4 File Classification — route by extension to correct parser parser
5 Parser Execution — extract entities from each file group parser
6 Relationship Building — connect entities with evidenced edges graph
7 Graph Validation — unique IDs, no orphan references graph
8 Graph Writing — serialize to atlas-graph.json storage

Data Model

Everything is an Entity. Connections are Relationships with evidence.

Entity

{
  "id":          "controller:hostedcluster.HostedClusterReconciler"
  "name":        "HostedClusterReconciler"
  "kind":        "controller"
  "package":     "hostedcluster"
  "watches":     ["HostedCluster", "Secret", ...]
  "source": {
    "parser": "go"
    "file":   "hostedcluster_controller.go"
    "line":   142
  }
}

Kinds: operator controller crd function package test document resource

Relationship

{
  "from":       "controller:hostedcluster.HCR"
  "to":         "crd:hypershift.HostedCluster"
  "type":       "reconciles"
  "confidence": "proven"
  "evidence": {
    "file":    "controller.go"
    "line":    142
    "snippet": "func (r *HCR) Reconcile(...)"
    "reason":  "controller has Reconcile() method"
  }
}

Types: reconciles creates tested_by

Confidence: proven (AST evidence) or inferred (naming convention)

Key Principles

  • ✓ IDs are deterministic — same commit = same graph
  • ✓ Every relationship carries evidence (file + line + snippet)
  • ✓ Store forward edges, compute inverses at load time
  • ✓ Two confidence levels only: proven or inferred
  • ✓ Unified entity model (one type, kind field)
  • ✓ No AI until the graph is proven correct

Architecture Decision Records

9 ADRs document the design rationale. Every major choice is recorded.

  • Scanner and viewers are separate — consumers never parse Go, they read JSON
  • JSON before Neo4j — reconsider graph DB only if JSON exceeds ~10MB
  • No AI until graph is proven — AI explains the graph, never populates it
  • Evidence on every relationship — no edge without file + line proving it
  • Typed relationships over generic edges — "reconciles" not "relates to"
  • Unified entity model — one Entity type with a kind field, no subclasses
  • Store forward edges, compute inverses — "calls" stored, "called_by" computed at load
  • The Atlas Graph is the product — improve the graph, every consumer improves
  • Deterministic over intelligent — same commit = same graph, always
